# 家庭点菜小程序 · 系统架构设计说明书

## 1. 系统概述

### 1.1 产品定位

面向家庭用户的饮食决策微信小程序，核心解决"今天吃什么"问题，围绕选菜→菜单→买菜→做菜→记录形成完整闭环。

### 1.2 技术选型

| 层级 | 技术栈 | 版本 |
|------|--------|------|
| 前端 | 微信小程序原生框架 | 基础库 2.x |
| 后端 | Spring Boot | 3.2.0 |
| 语言 | Java | 17 |
| 数据库 | MySQL | 8.0 |
| 数据访问 | Spring JdbcTemplate | - |
| 构建工具 | Maven | 3.x |

### 1.3 设计原则

- 单体优先：产品初期不引入微服务复杂度
- 渐进降级：读接口网络失败时返回空列表/默认值，核心写操作不伪成功
- 渐进增强：游客→注册→VIP 三级体验递进
- 数据闭环：所有状态服务端持久化，不依赖小程序本地缓存

### 3.3 API 失败处理策略

```
请求发起 → 服务端响应?
  ├─ 2xx → 返回数据
  ├─ 401 → 自动重新获取 guest token → 重试
  ├─ 读接口错误 → 返回空列表/默认状态并提示
  └─ 写接口错误 → 抛出错误，页面提示失败
```

核心设计：读链路允许空态降级，写链路必须等服务端确认，避免本地伪成功。

### 3.4 认证流程

```
App.onLaunch
  → 检查本地 auth_token
  → 调用 GET /api/auth/me 验证
  → 失效则 POST /api/auth/guest 获取新 token
  → 存入 Storage，后续请求自动携带 X-Auth-Token
```

### 4.3 认证机制

```
┌──────────┐     POST /api/auth/guest      ┌──────────────┐
│  客户端   │ ──────────────────────────────→ │  AuthService │
│          │ ← token + user info ────────── │              │
└──────────┘                                └──────┬───────┘
                                                   │
     后续请求携带 X-Auth-Token                       ▼
     ─────────────────────────────→  user_session 表验证
```

- 游客登录：基于 Device-Id 生成会话，无需微信授权
- 微信登录：预留 code2session 接口，后续替换
- Token 存储：user_session 表，含过期时间
- 权限分级：普通用户 / 管理员（is_admin 字段）

### 4.4 事务管理

关键写操作使用 `@Transactional` 注解：
- 创建菜谱（recipe + steps + ingredients 三表联写）
- 更新菜谱（先删后插 steps/ingredients）
- 今日菜单操作（menu + items + shopping_list 联动）
- 社区互动（post + comment_count 计数同步）

### 5.3 索引策略

- 复合唯一键：`uk_family_menu_date`（防止同一天重复菜单）、`uk_post_user`（防止重复收藏）
- 查询索引：按 status+source_type 筛选菜谱、按 audit_status 筛选社区内容
- 排序索引：cook_history 按时间倒序、shopping_list 按 family_id

## 6. 业务流程

### 6.1 核心闭环：选菜→做菜→记录

```
用户进入首页
  → 浏览推荐/筛选菜谱
  → 加入今日菜单 (POST /api/daily-menu/today/items)
  → 自动生成购物清单 (POST /api/shopping-list/today/rebuild)
  → 标记已购 (PATCH /api/shopping-list/today/items/{id})
  → 做完记录 (POST /api/cook-history)
  → 影响偏好画像 (GET /api/preference/profile)
```

### 6.2 导入配方流程

```
用户粘贴文本/链接
  → POST /api/import/preview（服务端解析）
  → 返回：标题、菜系、食材、步骤、置信度
  → 用户确认/修改
  → POST /api/recipes（保存为 imported 类型）
  → 保留 import_source 记录
```

### 6.3 社区内容治理

```
用户发帖 → audit_status = APPROVED（当前自动通过）
用户举报 → community_post_report (PENDING)
管理员审核 → APPROVED / REMOVED
  → REMOVED 时同步更新 community_post.audit_status
```

## 8. 安全设计

### 8.1 认证与授权

| 层级 | 机制 |
|------|------|
| 身份识别 | X-Auth-Token + X-Device-Id |
| 会话管理 | 服务端 user_session 表，含过期时间 |
| 权限控制 | requireAuthenticatedUser / requireAdminUser |
| 资源隔离 | 菜谱按 owner_user_id 校验，家庭按 family_id 隔离 |

### 8.2 输入校验

- Controller 层使用 `@Valid` + Jakarta Validation
- Service 层二次校验关键业务参数
- SQL 使用 PreparedStatement 防注入

### 8.3 CORS 配置

仅允许配置的 origins 访问，默认限制为 localhost。

### 9.2 技术债务

| 项目 | 风险 | 优先级 |
|------|------|--------|
| MysqlKitchenStore 过大 | 单文件 1000+ 行 | 中 |
| 无分页 | 数据量大时性能下降 | 中 |
| 无缓存层 | 高频查询直接打 DB | 低（当前量级） |
| 无日志审计 | 关键操作无追踪 | 低 |

## 10. 差异化设计要点

### 10.1 包名与标识

- 后端包名：`com.familymenu.daily`
- 项目标识：`family-menu-daily-server`
- 数据库名：`family_menu_daily_db`
- 前端标识：自定义 TabBar + 暖橙色系（#ff6b35）

### 10.2 产品差异化

- 以"家庭"为核心单位而非个人
- 菜谱来源三分法：自建/社区/导入
- 购物清单由菜单自动生成而非手动维护
- 食材库存反向匹配可做菜谱
- 口味偏好基于实际做菜记录而非问卷
