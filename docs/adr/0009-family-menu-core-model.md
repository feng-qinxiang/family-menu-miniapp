# 0009 — 家庭点菜核心模型:共享菜单 + 字典级食材对账

- 状态:accepted
- 日期:2026-06-20
- 关联:blueprint-v1.md(完整蓝图)

## 背景

用户反馈"显示和操作逻辑不对、不像家庭点菜小程序"。经 grilling 会话定位,根因不是配色/排版,而是信息架构重叠:"点菜"动作和"今日菜单"对象在 首页/菜谱/菜单 三个 tab 各出现一次,冰箱入口同时挂在 3 个 tab。需从产品模型层重定主线。

## 决策

### 1. 主线 = "今天吃什么"决策工具,今日餐桌当第一屏
点菜是主动作,冰箱对账/买菜清单是下游。四 tab:今日餐桌(当家)/菜谱/冰箱/我的,每个入口唯一化。否决了"内容社区型"(逛菜谱当家)和"库存 ERP 型"(冰箱当家)两种定位。

### 2. 今日菜单 = 家庭共享、全员可写、操作留痕
否决"掌勺单一写入者"(过于限制全家协作)和"纯自由无记录"(混乱不可追溯)。取中间:谁都能加删,但每次写 menu_operation_log。留痕替代审批流,代价最小,且白送家庭动态展示。

### 3. 食材对账 = 字典级精确(用户坚持"严丝合缝"),按计量方式分五类
建 ingredient + ingredient_alias 统一字典,recipe_ingredient/pantry_item 关联 ingredient_id。否决"自由文本模糊匹配"(番茄/西红柿对不上账,正是病根)。
按计量方式分五类各走各逻辑:可数(个/块)精确扣真账、可称(克/ml)精确扣真账、瓶袋装(瓶/袋)按 pack_size_ml 折 ml 估扣(是"该买信号"非真账)、整装手感(把/份)只判有无不扣量、无量(少许)不管。track_mode 来源三层 B>A>C(用户改>字典默认>category自动推断)。单位字典定死、录入不自由填(单位一致减法才成立),不求全、用着不顺再增删。这是 V1 不可逆地基。

### 3b. 瓶装 ml 估算定位 = 消耗进度条/该买信号,非精确库存
"生抽写瓶"图省事,但瓶减不出勺。取折中:字典定 pack_size_ml(1瓶≈500ml),做菜按标准量折 ml 扣,扣到阈值下次点菜时提示复核。明确这是估算信号,产品文案不承诺"精确剩余"。有/无档无法扣减,用"被用到→下次点菜待复核"补漏。

### 4. 标准用量与实际用量分离
菜谱标准量是"预填草稿"(共享级,不可被破坏),实际量是用户本餐确认值(扣冰箱用)。解决"系统标准 vs 我实际用量对不上"的伪矛盾——扣冰箱的从来是实际量,标准只负责少打字。

### 5. 偷懒默认按标准量自动扣减(方案 A)
做完一键"我做了",不填则按标准量扣;勤快改实际量。否决"不确认不扣"(单向虚高累积更坑)。误差靠手动盘点纠偏。

### 6. 盘点手动 + 拍照仅备忘,识图推迟
A+甲:手动改数 + 拍照留影,不做 OCR/视觉识别(真实冰箱叠放遮挡识别率低,初版翻车风险高)。但数据结构预留 image_url/source 字段,识图作 V2 可插拔增强。

### 7. 路线图 V1→V4 严格排序
V1 今日闭环(含字典地基)→ V2 周菜单+人人点单+识图 → V3 三档转盘(菜源限做过/收藏/社区收藏)→ V4 凑一桌组合推荐(人工规则)。最不确定的"搭配规则"垫底,等真实使用手感后再定。

## 后果

正面:信息架构去重,主线清晰;字典化对账让买菜清单可自动计算;留痕给家庭版温度。
负面/风险:字典是不可逆结构改动,需先空库验证;归一化别名表需持续运营;前端四主页 + tabBar 改造工作量大,建议先空壳验证结构。
正交遗留:支付/会员前端悬空(/api/payment/* 已就绪,前端仍调老 /api/vip/*),与本决策无关,另行安排。
