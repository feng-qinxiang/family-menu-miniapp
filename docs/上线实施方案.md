# 家庭点菜小程序 · 正式上线实施方案

> 版本：v1.0　制定日期：2026-09-10
> 视角：全栈 / 架构 / 测试　目标：从当前「本地可运行、功能完整」状态推进到微信小程序正式上线并稳定运营
> 前置阅读：`spec/LAUNCH-CHECKLIST.md`（运营侧清单）、`server/src/main/resources/application-prod.yml`（生产配置基线）

## 0. 总体结论（TL;DR）

当前项目**功能完成度约 85%，上线就绪度约 30%**。代码质量与测试基础良好（后端 74 个测试全绿、生产配置已做安全隔离），真正的缺口集中在 **「代码之外」**：服务器、域名 ICP 备案、HTTPS、微信小程序后台配置、CI/CD 与监控——这些是硬门槛，且 **ICP 备案（1~2 周）是关键路径，必须第一天启动**。

建议按 5 个里程碑推进，**总周期 4~5 周**（含备案等待）：

```
M0 准备(3天) → M1 基建与加固(1周) → M2 联调与测试(1周) → M3 提审与灰度(1~2周,含备案) → M4 正式发布+运维
                          ↑ ICP 备案在 M0 第一天提交，与 M1/M2 并行
```

| R7 | **隐私合规** | 🟡 中 | 需在 mp 后台声明相册/剪贴板/昵称三项（文案已在 `legal/privacy` 就位），缺《隐私政策》托管页 |

## 2. 架构设计

### 2.1 部署架构（生产目标态）

```
微信小程序 ──HTTPS──▶ Nginx(443, TLS终结, 反代, 限流, 静态资源)
                          │
                          ├── /api/*     ──▶ Spring Boot (127.0.0.1:8080, prod profile)
                          ├── /admin/*   ──▶ 同上（建议加 IP 白名单/二次验证）
                          └── /uploads/* ──▶ Nginx 直出或对象存储
                                                 │
                                          MySQL 8（本机或云 RDS，每日备份）
                                                 │
                                          文件存储：本地 UPLOAD_DIR（初期）
                                          → 二期迁移对象存储 COS/OSS
```

**选型决策（务实优先，个人项目不追过度设计）：**

| 项 | 选型 | 理由 |
|---|---|---|
| 服务器 | 单台云服务器 2C4G（腾讯云/阿里云轻量）起步 | 家庭工具类 QPS 极低；垂直扩容比分布式划算 |
| 数据库 | 云服务器自建 MySQL 8（或轻量 RDS） | 数据量小；自建省钱，RDS 省心，二选一 |
| 进程管理 | systemd 托管 jar | 自动拉起、开机自启、日志接 journald |
| HTTPS | Nginx + Let's Encrypt（certbot 自动续期） | 免费、微信认可 |
| 文件存储 | 初期本地 `UPLOAD_DIR` + Nginx 直出；**预留 COS 迁移口** | 避免一次性过度投入 |
| 登录 | 微信 `code2session`（`WECHAT_APP_ID/SECRET`） | 替换设备指纹为主登录，游客兜底 |
| 支付 | **个人主体：保持关闭**；企业主体：启用现有 `WechatPayService` + 平台证书验签 | 代码已双轨，开关切换即可 |
| 监控 | 日志（journald/logback 文件）+ 简单探活 + 云监控告警 | 不引入重型 APM |

### 2.2 接口设计原则（沿用现有契约，不推倒）

- 现有 REST 契约已在 `docs/支付与登录接口契约.md` 定义，**保持不变**；上线只改「实现来源」（mock → 真实微信接口），不改契约形状。
- 所有受保护接口继续走 `AuthInterceptor` + `@RequiresAuth/@RequiresAdmin/@RequiresPermission` 注解体系（已就位）。
- 生产必配环境变量见 `application-prod.yml` 注释清单（DB 强口令、微信凭据、`ADMIN_OPENIDS`、`CORS_ALLOWED_ORIGINS`、`UPLOAD_DIR`）。

### 2.3 数据模型

- 26 张表现状合理（家庭-成员-菜单-菜谱-社区-订单-审计边界清晰），**上线不做结构性变更**。
- 生产建库走 `sql/create-database.sql` + `schema.sql` 一次性执行；`SPRING_SQL_INIT_MODE=never` 已在 prod 固定，防止 `data.sql` 注入演示数据。
- 备份策略：`mysqldump --single-transaction` 每日定时 + 异地保留 7 天（脚本进 CI 或 crontab）。

## 5. 上线部署

### 5.1 环境与配置
- **环境划分**：本地（dev）→ 体验版（trial，连测试库）→ 正式（release，连生产库），靠 `env.js` + `SPRING_PROFILES_ACTIVE` 区分。
- **凭据管理**：一律环境变量注入，禁止入库入仓（prod 已强制）；DB 口令、AppSecret、支付证书单独保管。
- **生产 profile 红线**（已在 `application-prod.yml` 固定，部署时复核）：`sql.init.mode=never`、`auth.dev-otp-enabled=false`、`wechat.pay.mock-pay-enabled=false`、`app.seed-demo-data=false`。

### 5.2 CI/CD 流程
```
push/PR → GitHub Actions: mvn test（单测+接口）→ 打包 jar
   └─ main 合并 → 构建产物 → scp/ssh 到服务器 → systemctl restart → 健康检查
        └─ 健康检查失败 → 自动回滚到上一版 jar（见 5.4）
小程序端：开发者工具/CI 上传 → 体验版验证 → 提审 → 发布（微信平台，不走自建 CD）
```

### 5.3 灰度发布
- **小程序端**：用微信「分阶段发布」按 10% → 50% → 100% 放量。
- **后端端**：保留上一版 jar，先单实例观察日志/告警 24h 再视为稳定（单体架构下灰度靠「快速可回滚」而非多实例分流）。

### 5.4 监控告警与回滚预案
- **监控**：接口探活（`/actuator/health` 或轻量健康端点，每分钟）、错误日志关键字告警、云监控（CPU/内存/磁盘）告警到微信/邮件。
- **回滚预案（必须演练一次）**：
  1. 保留最近 3 个版本 jar + 对应数据库备份点；
  2. 回滚 = `systemctl stop` → 切回旧 jar → `start` → 健康检查，目标 **RTO < 5 分钟**；
  3. 若涉及 schema 变更，变更必须**向后兼容**（只加不删），使代码可独立回滚；
  4. 数据级回滚用每日 mysqldump 备份恢复，事先演练恢复流程。

## 6. 上线后运维

- **日志监控**：logback 按天滚动 + 保留 30 天；error 级日志接告警；审计日志（`admin_audit_log`）定期复盘管理操作。
- **用户反馈收集**：App 内反馈工单（已实现，后台有队列）为主渠道；建立「反馈 → 工单 → 修复 → 回复」闭环 SLA（P0 24h、P1 3 天）。
- **数据运营**：每周看后台数据看板（新增用户、发帖、菜单创建量），识别留存与活跃瓶颈。
- **内容安全运营**：举报队列每日清零，msgSecCheck 拦截率抽查，防止 UGC 违规被平台处罚。
- **后续迭代建议（按价值排序）**：
  1. 微信订阅消息（菜单提醒、愿望被采纳通知）——提升留存性价比最高；
  2. 文件存储迁移对象存储（COS/OSS）+ CDN——为图片增长做准备；
  3. 升级企业/个体户主体 → 开通真实微信支付与会员商业化；
  4. 菜谱详情「查看」弹窗（管理后台已知功能缺口）；
  5. 数据报表增强（留存漏斗、活跃度）。
