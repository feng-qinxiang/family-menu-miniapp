# 家庭点菜小程序全面分析

审计日期：2026-10-07  
审计范围：当前工作区代码、前后端测试、隔离数据库运行实例、微信开发者工具页面验证、静态配置与上线资料。

## 结论

项目已经具备可运行的家庭点菜闭环：菜谱浏览、菜单编排、库存、做菜记录、收藏、评论/内容审核、登录和管理能力均已落地。当前形态适合继续内测和修复，不适合直接提交正式版。主要原因不是功能缺失，而是几个会造成家庭数据错误或用户身份漂移的跨层一致性问题：库存扣减没有按数量和份数计算，做菜完成接口缺少足够的幂等边界，菜单覆盖会丢状态，登录续期可能换账号，以及上线配置仍含占位值。

项目规模约为 43 个注册页面、38 个业务页面、59 个主要 Java 文件、28 张表和 117 个 HTTP mapping。前端静态检查通过，隔离数据库后端测试为 232 tests / 0 failures / 0 errors / 0 skipped；微信开发者工具已实际检查首页、菜谱、菜单和库存页面。测试通过说明现有契约稳定，但没有覆盖下面列出的业务一致性缺陷，不能把通过率等同于上线就绪。

## 架构与现状

- 前端：原生微信小程序，主包约 1.41 MB，pkg-extra 约 0.58 MB，pkg-preview 约 0.14 MB，均低于 2 MB 分包限制。
- 后端：Spring Boot 3.2、Spring JDBC、MySQL；业务服务集中在菜单、库存、做菜、用户、UGC 和管理模块。
- 数据：家庭、用户、菜谱、菜单项、库存、烹饪记录、评论和审核等数据已分表，具备事务基础。
- 工程：已有前端逻辑测试、静态检查、交互体检和隔离数据库测试；当前审计还生成了可重复复现脚本和页面截图。

## P0：上线前必须修复

### 1. 库存可用性只看名称/单位，不看数量

客户端 `miniapp/utils/pantry-match.js` 和服务端 `EnhancedService.java` 都可能把库存 1 判定为满足需求 8 或 2。这样会在“库存看起来够用”的情况下继续做菜，造成库存负数前的错误提示、错误采购建议和家庭成员对库存的错误信任。

复现证据：`F06-client-stock-quantity`（stock=1, need=8, available=true）；`F06-server-stock-quantity`（stock=1, need=2, matchRate=1）。

修复要求：统一单位换算和数量比较口径；返回缺口数量；服务端在事务内再次校验，客户端结果只用于展示。

### 2. 做菜人数没有进入服务端扣库存计算

`MysqlKitchenStore.java` 按菜谱基准份数扣减，没有把用户请求的 servings 传入或换算。菜谱 4 份、请求 8 份时实际只扣 2 个单位，库存被系统性高估。

复现证据：`F04-serving-deduction`（initialStock=20, actualStock=18，预期为 16）。

修复要求：请求模型明确携带 servings；服务端按 `requested / recipeServings` 计算每种原料的扣减量，并在事务内锁定库存行、校验缺口、记录实际扣减。

### 3. 带评分的重复完成请求绕过 60 秒幂等

完成做菜后附带评分的路径会产生独立记录，并再次扣库存，现有 60 秒保护没有覆盖整个业务操作。网络重试、用户重复点击或客户端恢复都可能重复消耗库存。

复现证据：`F05-scored-retry`（separateRecords=true，库存 18 降至 14）。

修复要求：以客户端生成的 completion/request id 作为服务端唯一幂等键；“写烹饪记录、评分、扣库存、审计”必须在同一事务中按幂等结果返回，重试不得再次扣减。

### 4. 菜单餐次覆盖会删除原餐次及其状态

`TodayService.java` 在同一天从午餐加入晚餐时会删除原午餐项，且 item id 改变、已完成状态丢失。家庭成员会看到错误的餐次和完成记录。

复现证据：`F07-meal-overwrite`（remainingMeals 只有 dinner，lunchDoneRemoved=true，itemIdChanged=true）。

修复要求：菜单项唯一键至少包含 family、日期、餐次和菜谱；迁移/合并时保留两个餐次的独立状态，禁止用“同菜谱”覆盖另一餐次。

## P1：修复后再扩大内测

### 5. 周菜单重新生成被缓存直接短路

`EnhancedService.java` 在命中内存缓存时直接返回，显式“重新生成”不会产生新计划。缓存应服务于普通读取，不能吞掉用户明确的 regenerate 操作。

### 6. 清缓存会保留 token、删除 session_kind

`miniapp/utils/api.js` 清理逻辑删除会话类型但保留 `auth_token`，下一次续期走游客端点，可能静默切换到游客身份。

### 7. OTP 会话续期可能切换到微信身份

OTP 登录和微信登录都保存为 `session_kind=login`，续期依据类型选择 `/api/auth/login`，无法区分来源。OTP 过期后可能被当作微信登录续期。

### 8. 静默登录覆盖用户编辑过的昵称和头像

静默登录的 `upsertUser` 会把平台返回的昵称、头像写回用户资料，覆盖用户主动修改的资料。应区分平台身份字段和用户可编辑字段，只有首次绑定或用户明确同步时更新。

### 9. UGC 审核存在边界缺口

正文允许 5000 字符，但审核只检查前 2500 字符；图片审核响应为空或缺少 `errcode` 时可能被当作通过。需要审核完整正文，并把第三方响应缺失视为失败或待审，记录可追溯原因。

### 10. 离线许愿队列缺少可靠家庭绑定

离线队列没有把 family/user 身份作为不可变元数据绑定，切换家庭后补发可能落到错误家庭。队列项应带 family id、创建用户、版本和过期时间，服务端再次校验权限。

## P1：上线合规与运维门槛

- 注销页承诺删除或匿名化，但后端没有完整的自助注销接口，也没有覆盖内容、家庭 owner 转移和异步清理的闭环。
- 体验版和正式版 API 仍是 `example.com` 占位域名；运营者名称和联系方式也是占位符，不能提交审核。
- Compose/开发配置默认使用数据库 root；生产必须使用最小权限账号、独立密码和密钥注入。
- 尚未看到明确的 session/OTP 过期清理、上传配额与清理、备份恢复演练、关键业务埋点和告警。

## 做得好的地方

- 前端交互体检没有发现“有事件但缺按下反馈”或“可点但无事件”的高置信问题；仅有一个 64rpx 的重试按钮需要人工确认热区。
- 主包和分包体积受控，静态检查已把审核占位配置明确报出。
- 后端已有事务、审计和数据库测试基础，说明修复可以落在现有服务边界内，不需要重写架构。
- 首页、菜谱、菜单、库存页面已在微信开发者工具中实际打开并截图，基本页面链路可用。

## 建议修复顺序

1. 先修库存数量/份数、完成幂等和菜单餐次唯一性；为每项补一个失败复现测试。
2. 再修 session kind、OTP/微信续期和用户资料覆盖，增加跨登录方式测试。
3. 修 UGC 完整审核、离线队列家庭绑定和注销闭环。
4. 填写真实 HTTPS 域名、运营者资料，创建生产最小权限数据库账号。
5. 做真实微信登录、真机网络重试、多人并发、备份恢复和平台审核前检查。
